# Отчет по состоянию проекта Heat Tracer

## 1. Резюме

Проект представляет собой Java/Spring Boot сервис для моделирования трасс подключения к тепловым сетям в рамках конкурса «Лидеры цифровой трансформации» (ЛЦТ) 2026.

**Основная проблема**: Очень медленная генерация результата при качественной детализации схемы.

**Корневая причина**: Алгоритм построения графа видимости (visibility graph) имеет квадратичную сложность O(n²) по количеству вершин, где n — сумма всех углов полигонов ограничений + точек ОКС + кандидатов на врезку.

## 2. Анализ ТЗ (Техническое приложение ЛЦТ)

### 2.1. Входные данные
- **Формат**: GeoJSON FeatureCollection, EPSG:4326 (WGS 84)
- **Расчётная проекция**: EPSG:32637 (WGS 84 / UTM zone 37N)
- **Обязательные объекты**:
  - `oks_connection_point` — точки подключения ОКС с расходом `flow_tph` (т/ч)
  - `heat_network` — существующая тепловая сеть (LineString)
  - `heat_chamber` — существующие тепловые камеры
  - `source` — источник теплоснабжения
  - `restriction` с типами из таблицы 2 (обязательные):
    - `road`, `tram_tracks`, `gas_pipeline`, `power_cable`, `heat_network`, `water`
    - Дополнительные: `park`, `social_area`, `prohibited_site`

### 2.2. Правила построения сети
1. **Топология**: Древовидная структура без замкнутых маршрутов
2. **Углы поворота**: До 90° включительно, без необоснованных мелких изломов
3. **Разветвления**: Только в тепловых камерах (макс. 4 примыкания)
4. **Технические узлы**: Для изменения параметров (глубина, способ прокладки)
5. **Подход к ОКС**: Один финальный участок от границы полигона до точки подключения

### 2.3. Диаметры и предельная длина
| ДУ (мм) | Расход (т/ч) | Предельная длина (м) | Стоимость (руб/м) | Габарит (м) |
|---------|--------------|----------------------|-------------------|-------------|
| 100     | ≤25          | 400                  | 44 874            | 0.30        |
| 150     | ≤50          | 600                  | 59 832            | 0.35        |
| ...     | ...          | ...                  | ...               | ...         |
| 1000    | ≤2000        | 2000                 | 299 160           | 1.20        |

**Правило выбора ДУ**: Минимальный ДУ, удовлетворяющий BOTH расходу И предельной длине.

### 2.4. Пространственные ограничения (таблица 2)
| Тип | Запрещено | Спецпроход | Отступ (м) | Угол | Kспец |
|-----|-----------|------------|------------|------|-------|
| road | Нет | Да | 1.5 | ≥45° | 1.60 |
| tram_tracks | Нет | Да | 1.5 | ≥45° | 1.75 |
| gas_pipeline | Нет | Да | 2.0 | - | 1.25 |
| power_cable | Нет | Да | 2.0 | - | 1.15 |
| heat_network | Нет | Да | 1.0 | - | 1.05 |
| water | Да | Нет | 1.0 | - | - |
| oks | Да | Нет | 5/7/9* | - | - |

*Отступ для oks зависит от ДУ: <500мм → 5м, 500-800мм → 7м, ≥900мм → 9м

### 2.5. Выходные данные
GeoJSON с объектами:
- `heat_network` (новая сеть) с атрибутами: `diameter`, `flow_tph`, `laying_method`, `cost`, `depth_start`, `depth_end`
- `heat_chamber` (новая камера)
- `technical_node`
- `variant_summary` с итоговыми показателями

**Итоговый показатель** (чем меньше, тем лучше):
```
S = 0.7 · (C / 25 000 000) + 0.3 · (L / 100)
```
где C — стоимость (руб), L — длина (м)

```sql
p_task_id           UUID

p_new_diameter      INT

p_r_max_candidate   NUMERIC DEFAULT 2500.0
p_r_max_oks_corner  NUMERIC DEFAULT 500.0
```

**Алгоритм**:
1. Очистка таблиц `visibility_vertex`, `visibility_edge`
2. Создание вершин:
   - OKS points (кластер)
   - Tie-in candidates
   - Polygon corners (ограничено `p_max_corners=1500`)
3. Построение рёбер:
   - Corner-corner: R_MAX=200м
   - Corner-candidate: R_MAX=2500м
   - OKS-corner: R_MAX=500м
   - OKS-candidate: R_MAX=2500м
4. Фильтрация через forbidden zones (буферы ограничений)
5. Special passes (пересечения с коэффициентом)

## 4. Выявленные проблемы производительности

### 4.1. Квадратичная сложность построения графа

**Проблема**: Блок 5.1 (Non-OKS pairs) выполняет CROSS JOIN visibility_vertex × visibility_vertex с последующей фильтрацией:

```sql
WITH pairs AS (
    SELECT a.id AS a_id, b.id AS b_id,
           ST_MakeLine(a.geom, b.geom) AS line,
           ST_Distance(a.geom, b.geom) AS len
    FROM visibility_vertex a
    JOIN visibility_vertex b ON ...
    WHERE ... AND ST_DWithin(a.geom, b.geom, p_r_max...)
)
```

**Масштаб**:
- 88 полигонов ограничений × ~70 вершин = ~6160 углов
- После лимита `p_max_corners=1500`: 1500 corner vertices
- 17 OKS points → ~6 кластеров (2-7 точек на кластер)
- ~20 candidates на кластер

**Оценка количества пар**:
- Corner-corner: 1500² / 2 ≈ 1.1 млн пар × ST_DWithin + ST_Intersects
- Corner-candidate: 1500 × 20 = 30 000 пар
- OKS-candidate: 7 × 20 = 140 пар

**Время выполнения**: При 1500 corners и 20 candidates:
- ST_DWithin: ~50-100 мс на 100K пар
- ST_Intersects с union буфером: ~200-500 мс на 100K пар
- **Итого на один кластер**: 5-15 секунд

### 4.2. Отсутствие пространственного индекса для vertex

**Проблема**: Индекс `idx_vv_geom` создан, но запросы используют `ST_DWithin` внутри CTE, что не всегда эффективно использует GiST.

### 4.3. Неоптимальный порядок операций

Текущий порядок:
1. Генерация ВСЕХ пар в радиусе
2. Фильтрация через `ST_Intersects(line, forbidden_main)`

Оптимальный порядок:
1. Быстрая предварительная фильтрация (угол обзора, направление)
2. Генерация только перспективных пар
3. Точная проверка пересечений

### 4.4. Избыточная точность буферов

**V24** ввёл `p_oks_buffer_rough = 1.0` вместо 5/7/9м, что:
- ✅ Уменьшает объединение буферов соседних ОКС
- ❌ Но не решает проблему общего количества пар

### 4.5. Отсутствие кэширования между кластерами

Каждый кластер строит граф независимо, хотя:
- Polygon corners могут пересекаться между соседними кластерами
- Forbidden zones можно вычислить один раз на задачу

## 5. Соответствие кода ТЗ

### 5.1. ✅ Реализовано корректно

1. **Проекция**: EPSG:4326 → EPSG:32637 через `ST_Transform`
2. **Кластеризация ОКС**: DBSCAN eps=150м (соответствует логике группировки близких точек)
3. **Отступы для ОКС**: 5/7/9м в зависимости от ДУ (V14, V24)
4. **Специальные проходы**: Коэффициенты Kспец из `restriction_rules`
5. **Поиск пути**: A* через pgRouting `pgr_astar`
6. **Структура выходных данных**: GeoJSON с правильными типами объектов

### 5.2. ⚠️ Частично реализовано / Требует проверки

1. **Предельная длина ДУ**: В текущем коде нет явной проверки после построения пути
2. **Правило 4 примыканий к камере**: Не реализована валидация после построения графа
3. **Угол поворота ≤90°**: Нет проверки на "необоснованные мелкие изломы"
4. **Режим с глубиной**: Не реализован (допустимо по ТЗ п.5)
5. **Множественные варианты**: Возвращается только 1 вариант (ТЗ допускает до 3)

### 5.3. ❌ Проблемы соответствия

1. **railway/tram_tracks**: В dataset есть `restriction_type='railway'`, но в `restriction_rules` только `tram_tracks`. Это может привести к игнорированию ограничений.

2. **Таблица 2 ТЗ vs V7**: 
   - ТЗ требует `crossing_angle_max` для road/tram_tracks
   - В коде нет проверки угла пересечения

3. **Штраф за неподключение**: 100 000 000 + 500 000 · G — не реализован в экспортнике

## 6. План оптимизации производительности

### 6.1. Краткосрочные меры (1-2 дня)

#### 6.1.1. Уменьшение p_max_corners
**Текущее**: 1500  
**Рекомендуемое**: 300-500

Обоснование:
- Большинство углов полигонов избыточны для трассировки
- ТЗ не требует сохранения всех углов, только обоснованные повороты
- Тестировать на датасете: проверить connectivity графа

#### 6.1.2. Сокращение R_MAX для corner-corner
**Текущее**: 200м  
**Рекомендуемое**: 100-150м

Обоснование:
- Прямые участки длиннее 150м между углами ограничений редки
- Снижает количество пар в 2-4 раза

#### 6.1.3. Предварительная фильтрация по направлению
Добавить фильтр по углу между вектором направления и линией к цели:

```sql
AND ABS(degrees(ST_Azimuth(a.geom, b.geom)) - direction_deg) < 45
```

### 6.2. Среднесрочные меры (3-5 дней)

#### 6.2.1. Иерархический граф видимости

**Идея**: Строить граф в два этапа:
1. **Грубый граф**: Только ключевые вершины (ОКС, кандидаты, 100-200 главных corners)
2. **Локальное уточнение**: Для каждого найденного пути добавлять промежуточные corners

**Выигрыш**: 5-10x ускорение построения графа

#### 6.2.2. Materialized View для forbidden zones

```sql
CREATE MATERIALIZED VIEW mv_forbidden_zones AS
SELECT task_id, ST_Union(buf) AS geom FROM (...)
GROUP BY task_id;
```

**Выигрыш**: 2-3x ускорение (не пересчитывать буферы на каждый кластер)

#### 6.2.3. Параллелизация по кластерам

Текущий код в TaskService последовательный:
```java
for (OksCluster cluster : clusters) {
    visibilityGraphService.build(...);  // sequentially
}
```

Заменить на:
```java
clusters.parallelStream().forEach(cluster -> {
    visibilityGraphService.build(...);
});
```

**Выигрыш**: N-x ускорение (где N — число кластеров, обычно 4-8)

### 6.3. Долгосрочные меры (1-2 недели)

#### 6.3.1. Переход на JTS STRtree для построения графа

Перенести логику из SQL в Java:
```java
STRtree index = new STRtree();
// Индексация вершин
// Поиск соседей через query()
// Проверка пересечений через JTS
```

**Выигрыш**: 10-50x ускорение (JTS быстрее PostGIS для точечных операций)

#### 6.3.2. Алгоритм Visibility Graph через plane sweep

Вместо O(n²) пар использовать алгоритм заметания плоскости:
- O(n log n + k), где k — количество видимых рёбер
- Библиотека: CGAL или собственная реализация

#### 6.3.3. Упрощение геометрии полигонов

```sql
ST_SimplifyPreserveTopology(geom_utm, 2.0)  -- 2 метра точность
```

**Выигрыш**: 2-5x меньше вершин → 4-25x меньше пар
