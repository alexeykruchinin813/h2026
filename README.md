# heat-tracer — сервис моделирования трасс подключения к тепловым сетям

Решение кейса «Сервис моделирования трасс подключения к тепловым сетям»
конкурса «Лидеры цифровой трансформации» 2026.

## 1. Назначение и краткое описание

Сервис автоматически строит варианты подключения перспективных ОКС
(объектов капитального строительства) к существующей тепловой сети Москвы:
определяет точки врезки, строит трассы в обход запретных зон, рассчитывает
расходы и условные диаметры, оценивает стоимость, формирует выходной GeoJSON
по разделу 7 Технического приложения.

Работает полностью автоматически — без ручной правки маршрутов, координат
или конфигурации.

## 3. Архитектура алгоритма

### 3.1. Общий пайплайн (TaskService.runCalculation)

```
GeoJSON (до 3 ГБ) → input_feature (streaming)
↓
Валидация → task
↓
Граф существующей сети (GraphService)
↓
Кластеризация ОКС по DBSCAN (ClusterService)
↓
Кандидаты точек врезки (TieInService)
↓
Граф видимости (HybridVisibilityGraphService):
- SQL: build_visibility_graph (V25) — корни полигонов, кандидаты
- SQL: create_escape_points (V41) — escape-точки на границе OKS-буфера
- Java JTS: валидация рёбер по точным 5/7/9 м OKS-буфера
  ↓
  Поиск путей A* (PathFinderService, pgRouting pgr_astar)
  ↓
  Построение маршрута (RouteBuilderService):
- flow_tph на участках
- подбор ДУ (DiameterPicker)
- предельная длина (enforceMaxLength)
- стоимость, камеры, врезки
- ранжирование вариантов
  ↓
  Физическая сборка сети (PhysicalNetworkService.build):
- SQL: build_physical_network (V46/V50) — топология из рёбер путей
- SQL: prune_physical_cycles (V77) — разрыв циклов (артефакт ST_Node)
- SQL: cleanup_terminal_stubs (V78) — чистка висячих стубов, deg-2 камеры
- Java: cascadeSplitOverloadedNodes (V74) — сплит узлов degree > 4
- SQL: split_oversized_chambers (V53) — резервное дробление камер
- Java: mergeCoincidentNodes — слияние совпадающих узлов
- Java: dedupParallelSegments (V70) — слияние параллельных дублей
- Java: snapSegmentEndpoints — притяжка концов сегментов
- Java: fixCrossings (V76+) — планаризация X-пересечений и коллинеарных наложений (ТЗ 2.1)
- Java: dropZeroLengthSegments — удаление вырожденных сегментов
- Java: assignDiametersAndCosts — Ду по flow + предельная длина, стоимости
  ↓
  Координация врезок (TieInCoordinationService, min-cost flow / SSP)
  ↓
  Экспорт GeoJSON (ExportService.exportAllVariants)
```

### 3.2. Граф видимости

Задача: соединить OKS с кандидатами точек врезки в плотной городской
застройке, где прямые линии пересекают чужие буферы отступов.

**Гибридный подход (SQL + JTS):**

1. **SQL** строит coarse-граф:
   - `polygon_corner` — углы упрощённых полигонов (ST_SimplifyPreserveTopology, tolerance 2 м).
   - `candidate` — точки-кандидаты врезки.
   - `escape_point` — 8 равномерно распределённых точек на границе OKS-буфера
     (6 м = 5 м отступ + 1 м запас). Для MultiPolygon — 8 точек на каждую часть.
   - `oks` — точки подключения OKS.

2. **SQL** строит рёбра:
   - `oks → own escape_point` — выход из своего буфера (правило U6).
   - `escape_point → {candidate, polygon_corner, escape_point}` — мосты
     с фильтром только по **не-OKS** ограничениям (дороги, вода и т.д.).
   - Все рёбра single-direction; pgRouting вызывается с `directed := false`
     и `cost = reverse_cost`, что даёт двунаправленность без дубликатов.

3. **JTS** (Java) валидирует каждое ребро против точных буферов OKS:
   - 5 м при Ду < 500 мм
   - 7 м при Ду 500–800 мм
   - 9 м при Ду ≥ 900 мм
   
   Правило U6-extended: буфер **source**- или **target**-полигона ребра не
   проверяется (конец ребра легально лежит в своём буфере).

### 3.3. Совместное подключение OKS

Каждый OKS рассматривается как самостоятельная цель. Несколько OKS могут
использовать общий участок сети (это автоматически даёт merge на уровне
рёбер графа: если два пути OKS проходят через одно ребро, flow на ребре
суммируется).

Выходной граф новой сети — объединение `edge_ids` всех путей (по варианту).
На каждом ребре:
- `flow_tph` = сумма `flow_tph` всех OKS, чьи пути используют это ребро.
- `diameter` = минимальный подходящий по таблице 1 Технического приложения.
- Если непрерывный путь с одним Ду превышает предельную длину для этого Ду —
  Ду увеличивается (см. 3.4).

### 3.4. Расходы, Ду и предельная длина

Подбор Ду — в `DiameterPicker` по таблице 1 (18 значений от 50 до 1400 мм).
Для каждого OKS-пути:
- flow постоянный (равен flow этого OKS);
- Ду одинаковый на всех рёбрах пути.

**Предельная длина** (ТЗ 2.4) проверяется отдельно по каждому непрерывному
пути с одним Ду. Если суммарная длина превышает `maxLengthM` для этого Ду,
Ду всех рёбер сегмента повышается на один шаг и проверка повторяется
(до 5 итераций).

### 3.5. Содержательно отличающиеся варианты

`TaskService` формирует **основной вариант и до двух альтернатив** (ТЗ 2.8).
Реализованы три стратегии выбора точки врезки:

| Вариант | Стратегия | Отличие |
|---|---|---|
| `v1` | **Individual** — каждый OKS к своему ближайшему tie-in (min path cost) | Минимум длины путей, возможны новые камеры |
| `v2` | **Shared** — все OKS кластера используют один общий target | Минимум врезок, общий trunk |
| `v3` | **Sub-split** — кластер делится на 2 подгруппы по X-координате, каждая со своим shared target | Реализует признак ТЗ 2.8 «разделение на несколько частей сети» |

**Дедупликация.** После построения всех трёх стратегий `TaskService`
сравнивает `score` (округление до 4 знаков) и удаляет варианты с совпадающим
score. Гарантия: в финальном GeoJSON все варианты **содержательно отличаются**.

На наборе `first_dataset.geojson` все три стратегии дают содержательно
различные результаты — **3 варианта** в финальном GeoJSON:

- **v2** (rank 1): `score = 7.688665`, стоимость сети 73002555.98 ₽, длина 1881.53 м.
- **v3** (rank 2): `score = 8.504734`, стоимость сети 84328705.73 ₽, длина 2047.84 м.
- **v1** (rank 3): `score = 8.834698`, стоимость сети 94857635.53 ₽, длина 2059.56 м.

*(Метрики соответствуют текущему прогону с физической сборкой V70–V78,
SSP-координацией врезок и стоимостью камер по ТЗ 3.2 (`computeChamberCosts`);
исторические значения score до их внедрения — 15.81/15.82.)*

На разреженных наборах с альтернативными точками врезки возможны все **3**
варианта — механизм уже реализован.

### 3.6. Стоимость

| Компонент | Формула |
|---|---|
| Новый участок (base) | `L × cost_per_m(Du) × Kгл` |
| Новый участок (special) | `L × cost_per_m(Du) × Kгл × Kспец` |
| Новая камера | по таблице 3.2 (3М / 5М / 8М / 12М по макс. Ду) |
| Врезка в существующую камеру | 5 000 000 руб. |
| Штраф за неподключённый OKS | `100 000 000 + 500 000 × flow_tph` |

`Kспец` (специальные проходы — дороги, ЖД, газопроводы, кабели, существующая
теплосеть) берётся из `restriction_rules.special_k`. Если на ребре
пересекается несколько спец-проходов, применяется **наибольший** из Kспец
(ТЗ раздел 4).

`Kгл` = 1 в базовом 2D-режиме (см. раздел 4).

### 3.7. Физическая сборка сети и инварианты топологии (ТЗ 2.1, 2.3)

После ранжирования вариантов `PhysicalNetworkService.build()` собирает
физическую сеть (`physical_node` / `physical_segment`) и гарантирует
инварианты ТЗ:

**Порядок шагов в `build()`:**

```
build_physical_network (V46/V50)      — топология из рёбер путей
→ prune_physical_cycles (V77)         — разрыв циклов (артефакт ST_Node planarization)
→ cleanup_terminal_stubs (V78)        — чистка висячих стубов, переклассификация deg-2 камер
→ cascadeSplitOverloadedNodes (V74)   — сплит узлов degree > 4
→ split_oversized_chambers (V53)      — резервное дробление камер
→ mergeCoincidentNodes                — слияние совпадающих узлов (+ re-split)
→ dedupParallelSegments (V70)         — слияние параллельных дублей
→ snapSegmentEndpoints                — притяжка концов сегментов к узлам
→ fixCrossings (V76+)                 — планаризация пересечений (итеративно, до 200 проходов)
→ dropZeroLengthSegments              — удаление вырожденных сегментов после split-ов
→ удаление осиротевших узлов (degree=0)
→ assignDiametersAndCosts             — Ду по flow + предельная длина
→ computeChamberCosts                 — стоимость камер по ТЗ 3.2 (после assign: нужен max Ду)
→ recalcCosts → recount               — финальные стоимости и счётчики
```

**Каскадный сплит перегруженных узлов (V74).** Узлы существующей сети
(`existing_tie_in`, `branch_chamber`) могут принимать более 4 колёс.
Каждый такой узел `T` разбивается: создаётся камера `T'` на расстоянии
`TRUNK_LEN = 0.4 м` вдоль базовой трубы `w0`, первые 4 колеса остаются
у `T`, остальные переносятся к `T'`. Ствол `T→T'` — первый кусок `w0`,
коллинеарный существующей трубе; остаток `w0` перепривязывается к `T'`.
Все мутации выполняются через `NamedParameterJdbcTemplate` (исключён
рассинхрон позиционных аргументов). Цикл повторяется до исчерпания
перегруженных узлов (макс. 8 итераций) — сплит может каскадно
перегрузить соседний узел.

**Планаризация пересечений (V76+, `fixCrossings`).** Короткие коллинеарные
стволы V74 могут геометрически накладываться на соседние сегменты. Метод
итеративно (до 200 проходов) находит пары по предикату ТЗ 2.1 —
`ST_Intersects AND NOT ST_Touches` — и различает тип пересечения через
`ST_GeometryType(ST_Intersection(...))`:
- `ST_Point` (X-пересечение): оба сегмента разрезаются в точке пересечения
  (`ST_LineLocatePoint` + `ST_LineSubstring`) с созданием нового
  `technical_node`; если точка лежит ближе 0.1 % длины к концу сегмента —
  только перепривязка конца (без разреза);
- `ST_LineString` / `ST_MultiLineString` (коллинеарное наложение стволов V74):
  проход по endpoint'ам пересечения, разрез каждого сегмента, у которого
  endpoint строго внутри другого (один сплит за итерацию, затем перечитывание
  пары). Ветвь добавлена после того, как вариант только с `ST_Crosses` оставлял
  `bad_crossings=3`.
В отличие от удалённого `replanarize` (`ST_Snap(..., 0.05)` + `ST_Node`), метод
НЕ пересоздаёт топологию: OKS-узлы, tie-in и диаметры сохраняются
(прошлый вариант схлопывал стволы 0.4 м и терял OKS: 14 вместо 17).

**Разрыв циклов (V77, `prune_physical_cycles`).** Планаризация `ST_Node`
создавала циклы в физической сети. Функция удаляет по одному ребру на цикл,
предпочитая рёбра, удаление которых понижает degree `branch_chamber`
(экономия на камере).

**Чистка висячих стубов (V78, `cleanup_terminal_stubs`).** После V77 остаются
висячие узлы (`new_terminal_chamber`/`technical_node` deg=1) и degree-2 камеры.
Внешний цикл: удаление стуб-сегментов (deg=1 на конце, если и другой конец не
OKS/tie-in — защита от отрезания OKS), удаление осиротевших узлов,
переклассификация deg-2 камер. Выполняется для всех вариантов.

**Дедупликация параллельных сегментов (V70).** Сегменты с совпадающей
парой канонических концов (`ST_SnapToGrid(geom, 0.001)`) сливаются:
`flow_tph` суммируется в оставаемом, дубликаты удаляются.

Все инварианты ТЗ на конкурсном наборе зелёные, включая `bad_crossings=0`
(см. раздел 6.4).

## 4. Обработка OKS, для которых маршрут не найден

Если для отдельного OKS автоматический маршрут не найден:

1. `PathFinderService.findPathsFromOks` возвращает пустой список.
2. OKS учитывается в `unconnected_oks_ids` варианта.
3. Штраф по ТЗ 6: `100 000 000 + 500 000 × flow_tph` руб.
4. Пайплайн **не падает**: построенная для остальных OKS часть результата
   сохраняется (ТЗ 2.9).
5. В `variant_summary.unconnected_oks_ids` попадает ID (тип как в исходных
   данных — string/number) неподключённого OKS.

Порог `assertTrue(minWithPath >= 16)` в `HybridConnectivityIT` — регрессионный
барьер: на конкурсном наборе факт 17/17.

**Не допускается** намеренный отказ от подключения технически доступного
OKS для улучшения итогового показателя (Разъяснения п. 15).

## 5. Выходные данные

Один файл `result.geojson` (FeatureCollection, WGS 84 / EPSG:4326),
содержащий **все три варианта** одновременно. Варианты различаются
`properties.variant_id`.

### 5.1. Типы объектов

| `object_type` | Геометрия | Обязательные properties |

**История `bad_crossings`:** тестовый предикат —
`ST_Intersects(a.geom, b.geom) AND NOT ST_Touches(...)`. Ранняя версия
`fixCrossings` использовала `ST_Crosses`, который для коллинеарных наложений
стволов V74 (`cross_type=ST_LineString`, отрезки длиной 0.40 м с разными
`start_node_id`/`end_node_id`, поэтому `dedupParallelSegments` их не сливает)
возвращает `false` — метрика «застывала» на **3**. После расширения поиска пар до
предиката ТЗ и добавления ветви обработки линейных пересечений (см. раздел 3.7)
метрика стала **0**, тест зелёный.

## 7. Границы применения решения

**Что сервис делает:**
- Строит трассы в 2D (горизонтальная проекция).
- Подбирает Ду по расходу и предельной длине.
- Учитывает запретные ограничения (OKS, вода, ЖД, парк, соц. объекты,
  запрещённые территории) с отступами 1–9 м по ТЗ.
- Помечает спец-проходы (road, tram_tracks, gas_pipeline, power_cable,
  heat_network) с коэффициентами Kспец.
- Формирует три варианта и ранжирует по score.
- Экспортирует GeoJSON по разделу 7.

**Что сервис НЕ делает (Разъяснения п. 12–14 + ТЗ 2.12):**
- Не выполняет полный гидравлический расчёт (давление, потери напора,
  балансировка).
- Не выполняет реконструкцию существующей сети — по Разъяснениям п. 14
  в актуальной расчётной модели она не производится; поля
  `reconstruction_cost` остаются 0.
- Не строит продольный профиль в базовом режиме (2D).
- Не проектирует конструкцию камер и спец-переходов.
- Не готовит рабочую документацию.

**Ограничения алгоритма:**
- Пространственный поиск рёбер ограничен радиусом 500 м от escape-точки
  до кандидата (`ST_DWithin` в `create_escape_points`).
- Упрощение полигонов — tolerance 2 м, max 400 corners на кластер.
- Максимум 3 варианта (ТЗ 2.8).
- Предельная длина — 5 итераций повышения Ду.

## 8. Особенности реализации

### 8.1. Гибридный граф видимости (SQL + JTS)

Прямое построение графа видимости в SQL давало разрывный граф: углы
полигонов лежат внутри собственных буферов отступов, и SQL-фильтр
отбраковывал исходящие рёбра. Решение:
- SQL строит **coarse-граф** с маленьким буфером 0.5 м;
- JTS в Java валидирует каждое ребро против точных буферов
  (`PreparedGeometry` + `STRtree`);
- escape-точки на границе OKS-буфера обеспечивают выход из здания.

### 8.2. Устойчивость к MultiPolygon

OKS-полигоны часто передаются как MultiPolygon. `ST_ExteriorRing` от
MultiPolygon возвращает NULL. Решение — `ST_Dump(ST_Boundary(ST_Buffer(...)))`,
что даёт по одному рингу на каждую часть. Escape-точки создаются для
каждой части (для полигона с 5 частями — 40 точек).

### 8.3. Идемпотентность миграций

Все миграции, создающие функции, начинаются с `DROP FUNCTION IF EXISTS`
всех известных сигнатур. Тела функций используют
`#variable_conflict use_column` для избежания plpgsql-конфликтов
имён OUT-параметров и колонок.
